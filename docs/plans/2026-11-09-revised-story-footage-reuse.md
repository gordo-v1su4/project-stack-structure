# Revised-story reuse of same-project H3 footage

Status: local implementation; no live project writes, generation or deployment authorized by this plan.

## Outcome and boundaries

An owner can revise a confirmed treatment, Bible and scene phases, explicitly confirm a fresh creative baseline, place eligible existing H3 footage into current musical windows, generate only remaining holes, then review the assembled cut and consent to export. Historical job requests, targets, scopes, media and identity evidence remain unchanged. A historical prompt remains prior requested direction with `completion:unverified`.

This slice supports only origin jobs owned by the current authenticated owner in the exact current saved project. It neither chooses the final safe-copy strategy nor adds cross-project aliases/grants. A durable checkpoint is separate from permission to edit a project. No classifier, dependency, media duplication, upload disguise or asset-library rewrite is included.

## Contracts

- Keep origin provenance and current creative placement separate. Typed reuse placements retain original asset/job and selected source frame interval, while binding current target/song interval, generation baseline and fresh draft review. Old approvals do not approve a revised cut.
- Add an explicit creative-rebaseline mode using canonical generation-scope receipts/baselines and existing project revision/CAS. The existing additive-source equivalence path remains unchanged. A rebaseline validates a fresh confirmed story/Bible/source inventory, preserves canonical origin reference/media versions and current-reference migration, and issues a new scope. No old scope is reinterpreted as a new story.
- Reuse is bounded to exact original verified source frames at normal speed. Canonical job, issued policy, selected range, current-reference and first-frame gates remain mandatory. Current reference changes fail closed until supported current-reference revalidation; story changes stale current placement/review rather than historical identity facts.
- Coverage, preview, planner and export use the same typed placements. Reuse is only counted where it actually overlays the current cut. Native current-scope assets keep existing gates. A reused take validates against its original scope and its placement against the current scope; export must never equate them.
- Persist/hash the exact reuse selection and current creative review. Current story/Bible/source/target/media/proof/revision changes invalidate consent. Fresh assembled-draft acceptance and saved snapshot remain required before export.
- Bound collections and validate malformed/duplicate/foreign/rejected/out-of-range entries before dispatch. Raw owner/project job stores remain strict. Missing observed-source facts remain explicit; requested direction cannot become completed action.

## Implementation and release impact

Story confirmation retains canonical historical receipt/baseline coordinates and the existing current-reference migration, including pending-review provenance. It prepares fresh creative placements rather than modifying historical asset targets. An explicit `creative-rebaseline` source-confirmation mode prepares an immutable baseline candidate for the exact saved revision; project publication remains on the existing authenticated `If-Match` CAS save. Revised stories with origin footage must use this mode before missing-shot planning, so automatic first-generation enrollment cannot consume the new scope before its origin set is recorded. Unissued intermediate Story confirmations without completed footage grant no authority and are skipped; missing canonical authority for actual ready origins fails closed.

`reusedTakeReviewSha256` binds the placement, immutable origin fingerprint, historical identity evidence, actual per-take current-reference evidence and shared current-reference context. Eligibility evaluates an unrejected origin as a runtime pending candidate, so historical approval flags neither authorize nor veto fresh creative consent; stored approvals remain unchanged. Canonical same-project job, range, issued-policy, current-reference and first-frame checks still run. Fresh complete-cut acceptance grants current reuse consent. Native take approval behavior remains intact.

UI uses the existing take bank and assembled-draft review; reuse adds no player. The selection index falls back visibly when windows shrink, project changes remount transient controls, and reuse composition validates expensive origin evidence once per placement rather than once per cut fragment. Reload retains placement geometry and pending/accepted consent. Changed source/reference inventory is intentionally outside this v1; no generic migration or owner-only fallback is introduced.

This is a coordinated **worker and web** feature even though no task entry file changes. `src/trigger/localGeneration.ts` imports `runH3Generation` from `h3GenerationRunner.ts`, which consumes the changed `generationScopeServer.ts`; `src/trigger/h3ShotPlanning.ts` imports `executeH3ShotPlanning` from the changed `h3ShotPlanningServer.ts`. Shared draft, coverage and selected-footage modules also enter those bundles. Any release must refresh and verify the worker image and web together. Task IDs, Trigger SDK, queues, provider modes, dependencies and generation models are unchanged. This local work does not deploy either component.
