# Additive reference confirmation without orphaning completed footage

The reference library is part of the current source context. Appending unused sheets must require an explicit Story confirmation and a new cut review, while preserving unchanged canonical generation targets, policies, assessments and selected footage. The current placement input signature continues to detect all current inputs; a separately validated generation scope may retain the original signature only for a server-proven additive equivalence.

## Contract

- An authenticated source-confirmation request reads the owned project freshly and requires its exact remote revision. It creates an immutable, owner/project scoped equivalence receipt and returns a candidate, without writing the project. The caller saves that candidate with the same expected revision using project CAS. An older browser must reload on conflict.
- A normal project's first validated H3/first-frame preparation records a strong immutable source/semantic baseline. Later confirmation uses its exact reference manifest. Legacy recovery is limited to the exact R31 migration certificate: semantic SHA `d8dbc41874d603a6b6e4052b7302f72a37cbad3c3fe7e1a802e9c7082f070f3e`, original inventory SHA `8a5c066a8b28e817222635b234c62ded94bb61473d9e195989d43f33f5a9656b`, original reference SHA `0c0ed4b80709bb793dfbec41bdcbe91bfc9410c87e0ce4d96ad10ac693a76c93`, story SHA `bad46363a6b1dd2b66ee7e974e14037b79561ee741e82c7534aa46868144ea59`, and exact reprise/placement certificate below. A legacy FNV signature or reference subset match is insufficient evidence. Unanchored legacy footage stays banked and requires a new Story scope. Never trust a browser-supplied previous signature, reference manifest, receipt body, or exception.
- Equivalence permits only appended unused durable references. The original song, video inventory/media evidence, story text, windows, requirements, placements, source ranges, coverage policy and edit settings remain exact. Removing/replacing/relabeling an existing reference, changing media/story/settings/placements, or introducing a reference already used in the confirmed story is incompatible.
- A receipt binds owner, project, remote baseline revision, original/current source contexts, original/current placement input signatures, stable generation scope, strong semantic digest, preserved reference manifest, appended IDs and any narrowly admitted existing overlap. Subsequent appends use the prior canonical receipt as their original manifest. Stored receipt body and current semantic digest must be checked at dispatch, first-frame preparation and final export.
- New explicit Story confirmations use `generationScopeVersion: 2`: initial scope is a SHA256 of full editorial semantics plus strong current source/story context. Altering ranges, policy or settings changes scope before any append. Unmarked persisted legacy projects retain their exact old behavior until explicit new Story confirmation or the narrowly certified additive migration.
- Baselines and receipts bind raw-image ETag, full SHA256 and byte count, and master/video/chunk ETag plus total byte count. Original raw references use exact conditional reads against canonical generation reference proofs; newly appended images are initially pinned, conditionally read and hashed. Comparison never falls back to an unconditional old-object read. Full reference verification is bounded to 32 images/128 MiB with at most three concurrent reads. Media inventory is bounded to 128 objects, verified through conditional one-byte ranged GETs (not unsupported SDK HEAD).
- The sole R31 media bootstrap uses the exact historical 22-object/510,437,769-byte certificate represented by hashed key identities in `config/r31-source-media-bootstrap.json`. Current ETags are trusted only after a full streamed conditional GET matches every historical SHA and length. An immutable enrollment marker precedes every new baseline; a missing previously issued baseline cannot be recreated or re-pinned. Losing first-enrollment writes fail before GPU/artifact dispatch.
- Legacy projects without a receipt retain the existing input-signature behavior. Changed arrangements produce a new scope. Preview producers use the effective scope only after current-input freshness and local receipt integrity pass. Canonical server validators additionally read the immutable receipt.
- Confirmation preserves generated assets byte-for-byte and preserves selected IDs, increments the draft revision and clears cut review/consent, previews and export intent. Previously approved generated assets must be reviewed again. No job, target, issued policy or failed assessment is rewritten or aliased.
